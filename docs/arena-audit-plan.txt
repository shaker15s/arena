# MASÄR — MASTER REBUILD & PRODUCT EXCELLENCE SPECIFICATION

## الوثيقة التنفيذية الرئيسية لإعادة بناء المنتج

### إلى فريق Product / UX / UI / Mobile / Backend / QA / DevOps / Security

أريد التعامل مع مشروع **Masär — مسار** باعتباره **Product Rebuild / Product Excellence Project** وليس مجرد UI Redesign أو polishing للكود الحالي.

الهدف ليس أن يصبح التطبيق "شكله أحسن".

الهدف هو أن يصبح:

> **منتجًا حقيقيًا، بسيطًا، سريعًا، مفهومًا، موثوقًا، عربيًا من الدرجة الأولى، Accessible، Responsive، ممتعًا، وقابلًا للتوسع، بحيث يشعر المستخدم أن Masär هو أفضل طريقة لإدارة تجربته التدريبية، وليس مجرد نظام إداري آخر.**

# 01 — أهم قاعدة في المشروع

## DO NOT TREAT THE CURRENT UI AS THE PRODUCT SPECIFICATION

الـrepository الحالي هو:

* Implementation Baseline
* Source of truth for what currently exists technically
* مادة للتحليل
* مصدر لاكتشاف الـexisting functionality
* مصدر لاكتشاف الـtechnical debt

لكنه **ليس UX specification**.

لا تفترضوا أن:

* الشاشة الحالية صحيحة لأنها موجودة.
* الـnavigation الحالي هو أفضل navigation.
* الـcards الموجودة يجب أن تظل.
* الـfeatures الحالية يجب أن تظهر كلها للمستخدم.
* الـarchitecture الحالية هي أفضل architecture.
* الـdocumentation الحالية تمثل الحقيقة النهائية.
* أي animation موجودة معناها أن motion system جيد.
* أي accessibility props موجودة معناها أن التطبيق Accessible.
* وجود backend يعني أن الـflow production-ready.

كل claim يجب التحقق منه.

# 09 — Read Architecture

من أكبر المشاكل التي يجب إعادة تقييمها:

الـclient لا يجب أن يعتمد على فكرة:

> "هات كل الـdatabase ثم خليني أفلتر محليًا."

في الحالة الحالية يوجد read model مركزي كبير يجمع عددًا كبيرًا من الجداول في fetch واحد، والـRealtime يمكن أن يؤدي إلى إعادة تحميل هذا الـmodel بالكامل. هذه architecture يمكن أن تعمل في حجم صغير، لكنها ليست الطريقة المناسبة للنمو غير المحدود.

يجب الانتقال تدريجيًا إلى:

## Domain-oriented queries

مثل:

* getToday()
* getMyCourses()
* getCourseOverview(courseId)
* getBatchOverview(batchId)
* getBatchRoster(batchId)
* getSession(sessionId)
* getAttendanceForSession(sessionId)
* getMyCertificates()
* getLeaderboard(week)

بدل تحميل كل شيء.

* batches
* profiles
* certificates

* notifications
* everything

update attendance/session state.

### Server state

### Client state

# 13 — Idempotency

أي command يمكن أن يعاد تنفيذه دون إنشاء duplication.

مثال:

check-in

يجب ألا يؤدي إلى:

* duplicate attendance
* duplicate point event
* duplicate streak update

لو أُرسل الطلب مرتين.

استخدموا:

* idempotency keys
* unique constraints
* server authority

---

# 14 — Transaction Boundaries

أي action business-critical يجب أن يكون transactionally safe.

أمثلة:

### Enrollment

لا يمكن أن يدخل شخصان آخر مقعد بطريقة race condition.

### Certificates

لا يمكن إصدار شهادة لشخص غير مؤهل.

### Attendance

لا يمكن تكرار check-in بطريقة تؤثر على الإحصاءات.

### Kudos

لا يمكن تجاوز quota.

### Batch scheduling

لا يجب أن يحدث:

* instructor conflict
* room conflict
* session overlap

كل هذا يجب أن يكون server-side.

# 15 — Current known architecture concerns يجب إعادة التحقق منها

لا تفترضوا صحة أو خطأ أي نقطة بدون verification.

لكن يجب specifically audit:

### A

Global read model / large fetch.

### B

Realtime-triggered full refresh.

### C

Offline writes.

### D

Room scheduling collisions.

### E

Certificate on-screen QR correctness.

### F

Roster/report PDF behavior.

### G

E2E authentication.

### H

Race-condition testing.

### I

Device-specific behavior.

### J

Documentation drift.

الـforensic audit الحالي نفسه أشار إلى هذه المناطق تحديدًا، ومنها أن certificate QR المعروض على الشاشة historically كان يشفّر token ليس URL بينما نسخة PDF تستخدم URL صحيح، وأن roster export المسمى PDF كان CSV. يجب على الفريق إعادة اختبار ذلك على آخر code state قبل اعتبار أي finding نهائيًا.

# 16 — Security

لا تعتمدوا على UI permissions.

الـclient يمكن التلاعب به.

كل security-sensitive operation يجب أن تكون محفوظة server-side.

قاعدة:

> UI hides things.

لكن:

> Backend enforces authorization.

يجب اختبار:

* privilege escalation
* unauthorized record access
* unauthorized mutations
* role changes
* branch isolation
* organization isolation
* IDOR
* leaked sensitive fields
* stale sessions
* token abuse
* replay attacks
* QR replay
* QR forgery
* certificate forgery
* invitation abuse
* join-code abuse

يجب تصميمه كـsecurity-sensitive protocol.

يجب تعريف:

* token format

* session binding
* user binding
* signature
* replay prevention
* duplicate prevention

طالب يأخذ screenshot للـQR.

إذا نعم، هناك problem.

السؤال:

هل يستطيع طالب تسجيل حضور طالب آخر؟

إذا نعم، هناك severe problem.

# 19 — Touch targets

لا تعتمدوا على visual size فقط.

مثلاً icon صغير 20x20 ممكن يكون مقبول بصريًا، لكن الـinteractive target يجب أن يكون كبيرًا بما يكفي.

WCAG 2.2 Target Size Minimum يضع 24×24 CSS px كحد أدنى في حالات pointer input مع استثناءات محددة.

وبالنسبة لتصميم mobile-native:

استهدفوا controls أكبر، مع spacing واضح.

Apple نفسها توصي بحجم default 44×44 points على iOS، وتؤكد أن spacing بين العناصر مهم كذلك.

# 24 — Dynamic Type / Font Scaling

اختبروا:

100%

125%

150%

175%

200%

بدون:

* clipped text
* overlapping buttons
* inaccessible actions
* broken cards

وفي React Native يجب الاستفادة من font scaling بدل بناء UI يعتمد على أحجام نصوص ثابتة لا تتحمل التوسع.

# 25 — Reflow

* 320 px
* 360 px
* 375 px

# 36 — Motion Philosophy

Motion ليس decoration.

Motion يجب أن:

* explain
* orient
* confirm
* reward
* connect

Apple توصي بأن تكون motion purposeful، brief، precise، وألا تعوق المستخدم، مع توفير بدائل مثل haptics/audio حيث المناسب.

---

# 37 — Motion hierarchy

اعتمدوا نظامًا واضحًا:

### Micro

80–160ms

* press
* icon state
* tiny feedback

### Fast

160–220ms

* selection
* small transitions

### Standard

220–300ms

* screen transitions
* card expansion

### Emphasis

300–500ms

* success
* important feedback

### Celebration

500–900ms

* streak
* badge
* level-up

لا تجعلوا كل شيء يتحرك.

# 39 — Motion Anti-patterns

ممنوع:

* random floating objects
* infinite decorative animations
* excessive bounce
* parallax بلا معنى
* unnecessary blur animation
* screen transition طويلة
* motion في كل card
* animation قبل كل navigation
* decorative particles في كل مكان

---

# 40 — Reduced Motion

يجب احترام:

`prefers-reduced-motion`

والـplatform reduced-motion settings.

عند التفعيل:

* reduce translation
* remove unnecessary scale
* remove repeated loops
* remove celebration explosions
* replace spatial transitions with fade

Apple توصي صراحة بتقليل zoom/scaling/peripheral motion عند Reduce Motion، وتفضيل fades على الحركة المحورية.

WCAG 2.2 يتناول كذلك animation from interactions وإمكانية تعطيل motion غير الضرورية.
