# من عرض تجريبي إلى منتج حقيقي — Masar 3.1

هذه الوثيقة تشرح: ماذا أُزيل من «الوهمي»، ماذا صار حقيقيًا، ومقارنة بالتطبيقات
المنافسة الحقيقية مع خطة سدّ الفجوات.

---

## 1) ما أُزيل نهائيًا (لا وجود لأي شيء تجريبي)

| العنصر المحذوف | البديل الحقيقي |
|---|---|
| الدخول برقم الهاتف + OTP وهمي (`246810`) | Google OAuth عبر Supabase Auth فقط |
| «تجربة سريعة» بأربع شخصيات جاهزة (عمر/سارة/محمود/الأدمن) | لا يوجد — الدخول بحساب حقيقي فقط |
| شريط «وضع العرض التجريبي» + زر «إعادة ضبط بيانات العرض» | حالة مزامنة حقيقية مع الخادم + زر تحديث |
| قاعدة بيانات مبذورة في `src/data/seed.ts` تعمل من الذاكرة/localStorage | قراءة/كتابة فعلية في Postgres عبر `src/data/remote.ts` |
| مفاتيح Supabase مكتوبة داخل الكود | متغيرات بيئة `EXPO_PUBLIC_SUPABASE_*` فقط، وبدونها يظهر «الإعداد مطلوب» |
| زمن استجابة مُصطنع (`setTimeout` داخل mutate) | زمن الشبكة الحقيقي |
| جُمَل توضيحية تشرح محتوى كل شاشة (أونبوردينج، شرح القواعد، تلميحات…) | عناوين وبيانات فقط |

> بيانات البذر بقيت **كـ fixtures للاختبارات فقط** في `scripts/fixtures/seed.ts`
> ولا تُشحن مع التطبيق.

## 2) كيف صار التطبيق حقيقيًا؟

### الدخول
1. `المتابعة بحساب Google` → `supabase.auth.signInWithOAuth({ provider: 'google' })`
   (ويب: إعادة توجيه — موبايل: `expo-web-browser` + deep link `masar://auth/callback`).
2. تريجر `handle_new_user` ينشئ بروفايل تلقائيًا ويسحب من Google: **الاسم، الإيميل، الصورة**.
3. لأن رقم الموبايل ناقص → التطبيق يفتح شاشة **«أكمل بياناتك»**:
   الصورة (قابلة للتغيير ورفعها على Storage)، الاسم (قابل للتعديل)،
   الإيميل (يُعرض ويُحفظ ولا يُعدَّل)، رقم الموبايل (مطلوب)، النوع، والفرع.
4. بعد الحفظ يدخل المستخدم بدوره الحقيقي (student / volunteer / supervisor / admin).

### البيانات
- `fetchRemoteDb()` يقرأ 22 جدولًا ويحوّلها لنموذج التطبيق.
- `pushDelta(before, after)` يقارن الحالة قبل/بعد أي عملية ويكتب INSERT/UPDATE/DELETE فعليًا،
  فكل زر في الواجهة صار عملية سيرفر حقيقية دون إعادة كتابة الشاشات.
- كل المعرّفات المولّدة صارت **UUID v4** لتتوافق مع أعمدة Postgres وتحافظ على العلاقات.
- `subscribeRealtime()` يعيد التحميل فور أي تغيير في الجلسات/الحضور/الإشعارات/الأعذار.
- كاش محلي لعرض آخر نسخة عند انقطاع الشبكة + إعادة مزامنة عند عودة الاتصال أو فتح التطبيق.

### الأمان
`supabase/migrations/0004_real_auth_and_policies.sql`:
- السياسات القديمة كانت تقارن `auth.uid()` بأعمدة تشير إلى `profiles.id` → كانت تمنع كل الكتابة.
  استُبدلت بدوال `my_profile_id() / my_role() / is_staff() / is_admin()`.
- سياسات كتابة صحيحة لكل جدول (الطالب لنفسه، الطاقم لمجموعاته، الأدمن للكل).
- bucket `avatars` عام للقراءة وخاص للكتابة على مجلد المستخدم.
- تفعيل Realtime للجداول الحية.

## 3) مقارنة بالتطبيقات الحقيقية المنافسة

| القدرة | OneTap | Qwickly Attendance Plus | i-Attend / AttendEase | مسار (الآن) |
|---|---|---|---|---|
| QR للحضور | ✅ | ✅ (يتجدد باستمرار) | ✅ | ✅ QR دوّار كل 25 ثانية + كود احتياطي |
| منع الحضور بالنيابة | جيوفنسينج + نافذة زمنية | تأكيد الموقع + NFC | IP/RFID | التوكن الدوّار فقط |
| وضع كشك (Kiosk) | ✅ | — | ✅ | ❌ |
| تقارير وتصدير (CSV/PDF/Excel) | ✅ | ✅ | ✅ | ❌ |
| تنبيهات غياب تلقائية | ✅ | ✅ | ✅ | إشعارات داخل التطبيق فقط |
| عمل بدون إنترنت | AttendEase ✅ | — | ✅ | قراءة فقط (كاش) |
| شهادات قابلة للتحقق | عبر تكامل | — | ✅ | ✅ سيريال + صفحة تحقق عامة |
| جيميفيكيشن (نقاط/ستريك/دوري/شارات) | ❌ | ❌ | ❌ | ✅ **ميزة تفوّق** |
| تعدد الفروع واللجان | جزئي | عبر الـ LMS | ✅ | ✅ |

المصادر: صفحات المنتجات الرسمية لـ OneTap و Qwickly Attendance Plus و i-Attend
ومقارنات 2025 لأنظمة حضور الـ QR.

## 4) الفجوات المتبقية (مرتبة حسب الأثر)

1. **تأكيد الموقع (Geofencing)** عند تسجيل الحضور — أقوى مانع للتحايل بعد التوكن الدوّار.
2. **تصدير التقارير** CSV/PDF لكل مجموعة وجلسة وفرع (مطلب أساسي لدى كل المنافسين).
3. **طابور حضور دون إنترنت** (تخزين محلي ثم رفع تلقائي عند عودة الشبكة).
4. **إشعارات Push حقيقية** (Expo Notifications + جدول `push_tokens`) بدل الإشعارات داخل التطبيق.
5. **وضع الكشك** على جهاز لوحي في مدخل القاعة.
6. **دعوات بالبريد/الواتساب** لانضمام المتطوعين والمشرفين بدور محدد مسبقًا.
7. **تكامل تقويم** (ICS) لإضافة الجلسات لتقويم الطالب.
8. **NFC** كوسيلة حضور بديلة على الأجهزة الداعمة.

## 5) الهوية البصرية

Apple Liquid Glass صار الثيم **الأساسي** وليس خيارًا:
- كل البطاقات تستخدم ضبابية حقيقية (`expo-blur`) فوق خلفية متدرجة بكرات ضوئية.
- شريط التبويب زجاجي بضبابية حقيقية.
- الثيم يتبع النظام افتراضيًا (فاتح/داكن/OLED) ويُحفظ اختيار المستخدم.
